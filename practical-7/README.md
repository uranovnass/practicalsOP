# Практическая работа № 7. Межпроцессное взаимодействие (IPC)

## 1. Цель работы

Изучить основные механизмы межпроцессного взаимодействия (Inter-Process Communication, IPC) в Linux и Python. Реализовать обмен данными между процессами с использованием именованных каналов FIFO, Unix-сокетов, разделяемой памяти и каналов `Pipe`.

## 2. Задачи работы

В ходе выполнения практической работы необходимо:

- реализовать клиент-серверное взаимодействие через FIFO;
- создать сервер на основе Unix-сокетов с поддержкой нескольких клиентов;
- передать массив данных между процессами с использованием `multiprocessing.shared_memory`;
- реализовать передачу данных через `multiprocessing.Pipe`;
- сравнить время выполнения и особенности разных механизмов IPC;
- проверить корректное освобождение системных ресурсов.

## 5. Реализация

### 5.1. Обмен данными через FIFO

FIFO (First In, First Out) — именованный канал, позволяющий обмениваться данными между независимыми процессами.

В данной реализации сервер получает математическое выражение от клиента, вычисляет результат и возвращает его через отдельный канал.

**Алгоритм работы:**

1. Сервер создаёт именованный канал для запросов.
2. Клиент формирует выражение и отправляет его серверу.
3. Сервер получает запрос и вычисляет результат.
4. Результат передаётся клиенту через отдельный FIFO.
5. После завершения работы временные каналы удаляются.

**Пример запроса:**

```text
12*(3+2)
```

Ожидаемый результат:

```text
60
```

Другие примеры:

| Выражение | Результат |
|---|---:|
| `100/4` | `25.0` |
| `2**10` | `1024` |

FIFO обеспечивает обмен данными, но для согласования чтения и записи необходимо учитывать порядок операций и поведение процессов при открытии каналов.

### 5.2. Обмен данными через Unix-сокеты

Unix-сокеты обеспечивают двусторонний обмен данными между процессами на одной машине.

Сервер ожидает подключения клиентов и обрабатывает каждое подключение в отдельном процессе, что позволяет обслуживать нескольких клиентов одновременно.

**Алгоритм работы:**

1. Сервер создаёт сокет семейства `AF_UNIX`.
2. Сокет связывается с адресом в файловой системе.
3. Сервер ожидает подключения клиентов.
4. Клиент подключается и отправляет выражение.
5. Сервер вычисляет результат и отправляет ответ.
6. После остановки сервера временный файл сокета удаляется.

Примеры запросов и ответов аналогичны реализации FIFO.

Преимущество Unix-сокетов — двусторонний обмен данными и возможность построения клиент-серверных приложений с несколькими подключениями.

### 5.3. Разделяемая память

Разделяемая память позволяет нескольким процессам обращаться к одной области оперативной памяти без необходимости передавать весь массив через канал связи.

В эксперименте используется массив из **10 000 000 чисел**.

Программа:

1. Создаёт область разделяемой памяти.
2. Заполняет массив числами от 1 до 10 000 000.
3. Передаёт информацию, необходимую дочернему процессу для доступа к массиву.
4. Дочерний процесс вычисляет сумму элементов.
5. Измеряется общее время выполнения.
6. После завершения процессы закрывают доступ к памяти, а созданный сегмент освобождается.

Ожидаемая сумма элементов:

```text
50000005000000
```

Размер данных составляет приблизительно **76,29 MiB** при хранении каждого числа в формате 8 байт.

Разделяемая память особенно полезна при работе с большими массивами, поскольку позволяет избежать копирования всего массива между процессами. При этом необходимо правильно организовать доступ к данным и очистку ресурсов.

### 5.4. Передача данных через Pipe

`multiprocessing.Pipe` создаёт канал связи между процессами. Один процесс отправляет данные, а другой получает их.

В эксперименте массив из 10 000 000 чисел передаётся через `Pipe`, после чего принимающий процесс вычисляет сумму элементов.

Измеряется время передачи и обработки данных.

В отличие от разделяемой памяти, `Pipe` предполагает передачу данных через канал. Поэтому при работе с большими объёмами данных могут возникать дополнительные расходы на сериализацию, копирование и передачу.

## 6. Результаты эксперимента

Эксперимент выполнен для массива из 10 000 000 чисел. В обоих случаях получена одинаковая сумма.

| Показатель | Shared Memory | Pipe |
|---|---:|---:|
| Количество чисел | 10 000 000 | 10 000 000 |
| Размер данных | 76,29 MiB | 76,29 MiB |
| Сумма элементов | 50000005000000 | 50000005000000 |
| Измеренное время | 0,8632 с | 0,6029 с |

В данном запуске вариант с `Pipe` завершился быстрее примерно на 0,26 секунды.

**Важно:** измерения отражают время, полученное в конкретном запуске программы. Время для разделяемой памяти включает заполнение массива, создание процесса и вычисление суммы. Для `Pipe` учитываются передача, получение и обработка данных. Поэтому эксперимент не является чистым измерением скорости передачи и не доказывает, что `Pipe` всегда быстрее разделяемой памяти.

## 7. Сравнение механизмов IPC

| Механизм | Требуется ли синхронизация | Типичные данные | Особенности |
|---|---|---|---|
| FIFO | Да, необходимо согласовывать чтение и запись | Поток байтов, текстовые сообщения | Простая связь через именованный канал |
| Unix-сокеты | Да, требуется согласованный протокол обмена | Поток байтов, сообщения прикладного протокола | Двусторонний обмен и несколько клиентов |
| Shared Memory | Да, если процессы одновременно изменяют общие данные | Большие массивы и структуры данных | Нет необходимости передавать весь массив через канал |
| Pipe | Да, необходимо учитывать порядок передачи и завершение каналов | Поток данных между процессами | Удобная передача данных между связанными процессами |

Необходимость синхронизации зависит от конкретной реализации. Например, если разделяемая память используется только для чтения после заполнения, сложная синхронизация доступа к самим элементам может не потребоваться.

## 10. Контрольные вопросы

### 1. Почему разделяемая память обычно считается самым быстрым способом IPC?

Процессы обращаются к одной области памяти, поэтому им не нужно каждый раз передавать весь массив через отдельный канал. Это особенно эффективно при работе с большими объёмами данных. Однако фактическая производительность зависит от реализации и дополнительных операций.

### 2. Почему разделяемая память считается более опасной с точки зрения ошибок?

Несколько процессов могут обращаться к одним данным одновременно. Если они одновременно изменяют данные без синхронизации, возникают состояния гонки и некорректные результаты. Кроме того, необходимо следить за временем жизни сегмента и освобождать ресурсы.

### 3. Что произойдёт, если записать данные в Pipe, у которого нет читающего конца?

Поведение зависит от того, закрыт ли читающий конец. Если все дескрипторы чтения закрыты, запись в Unix-канал обычно приводит к сигналу `SIGPIPE` или ошибке `BrokenPipeError` в Python. Если читающий конец остаётся открытым, но данные никто не читает, канал может заполниться, и запись заблокируется.

### 4. Чем FIFO отличается от Unix-сокета?

FIFO — именованный канал для обмена потоком данных. Unix-сокет поддерживает двусторонний обмен и позволяет организовать клиент-серверное взаимодействие с несколькими подключениями.

### 5. Для чего используется Pipe?

`Pipe` обеспечивает обмен данными между процессами. Один конец используется для отправки, другой — для получения. Этот механизм удобен для передачи результатов вычислений и сообщений между процессами.

### 6. Зачем требуется очистка ресурсов после завершения программы?

Незакрытые каналы, временные файлы и сегменты разделяемой памяти могут оставаться в системе и мешать повторному запуску. Поэтому необходимо закрывать соединения и освобождать созданные ресурсы.
